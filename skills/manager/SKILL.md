# Manager

Два режима: **запись** переносит итог сессии в задачу, **чтение** отвечает, что с задачей сейчас.

## Развилка: где лежат задачи

Сначала прочитай файл правил штаба и файл правил отдела (`AGENTS.md` или `CLAUDE.md`).

- Задачи лежат в файлах (`tasks/`): работай по разделу «Уровень 1», остальной документ не нужен.
- Задачи в GitHub issues: работай с раздела «Уровень 2: задачи в GitHub issues».
- Строки о том, где лежат задачи, нет: предложи её дописать, например «Задачи отдела лежат в `tasks/`», и спроси человека до первой записи.

## Уровень 1: задачи в файлах

Запись, в конце сессии:

1. **Найти задачу.** Ищи задачу этой сессии в `tasks/` отдела (путь из правил: где лежат задачи). Файла нет: создай `tasks/<ГГГГ-ММ-ДД>-<slug>.md` с разделами:

   ```markdown
   # <название задачи>

   ## Результат
   ## Контекст
   ## Как проверить
   ## Текущее состояние
   ## Следующий шаг
   ## Результат и решение человека
   ```

2. **Обновить файл задачи.** Перепиши «Текущее состояние» (что сделано и где лежит) и «Следующий шаг» (одно действие). «Результат и решение человека» заполняет человек; агент переносит туда только его слова из сессии.
3. **Файл дня.** Допиши строку со ссылкой на файл задачи в файл дня штаба: путь из правил штаба, по умолчанию `tasks/<ГГГГ-ММ-ДД>.md` в штабе. Формат строки: `- <отдел>: <что сделано> → ../<отдел>/tasks/<файл>.md`.
4. **Саммари в чат:**

   ```
   ✓ сделано: ...
   ✎ ждёт человека: ...
   дальше: ...
   ```

Чтение: «что по <задаче>» ищется по `tasks/` отделов из карты отделов штаба; ответ берётся из разделов «Текущее состояние» и «Следующий шаг».

## Уровень 2: задачи в GitHub issues

Источник правды по задаче — GitHub issue: тело, состояние, лейблы, эпик. Доска (GitHub Project) показывает, что активно на неделе, и обновляется вслед за issue.

1. **Запись** — в конце сессии: прочитать, что сделано; найти существующие issues; обновить их прогрессом и комментарием о работе; соблюсти инварианты эпика, W-label и доски; новый issue создать, только когда ни один не подошёл.
2. **Чтение** — в любое время: «что по <задаче>» → поиск по репозиториям из конфига, сжатое состояние найденных issues с эпиком, лейблами, колонкой доски и последней активностью.

Все операции с issue (прочитать, изменить, записать, синк доски) идут через manager: он держит контракт записи, инварианты и синк доски.

Работа по задаче человека начинается с issue: до первой правки файла, коммита или записи наружу агент находит или создаёт issue в репозитории-владельце. Каждый коммит несёт `refs owner/repo#N`, ход работы идёт записью о работе, закрытие идёт комментарием Proof.

**Записи в GitHub делает скрипт `scripts/gh_issue.sh`**: `read`, `create`, `ensure`, `comment`, `shot`, `now`, `close`, `block`, `board`. Он печатает одну строку JSON, повторный запуск безопасен, `--dry-run` показывает мутации без отправки. Доска и id статусов берутся из `config.json` (пример: [config.example.json](config.example.json)). Команды, правила и примеры: [references/script.md](references/script.md).

**Итог — канбаном.** Есть инструмент визуализации (виджет в чате, холст) — итог сессии и ответ на чтение рисуй им канбаном: колонки «Ждёт вас» (первой, нумерованные действия человека глаголом и когда), «Идёт», «Сделано»; карточка — одна мысль обычными словами, ссылка на issue или PR внутри карточки. Текст после канбана не повторяет карточки, только то, чего в канбане нет: время до события, адреса, предупреждения. Инструмента нет — тот же канбан текстом по трём разделам.

**Язык сообщений человеку.** Каждое сообщение и итог пишутся обычными словами в информационном стиле: сначала что изменилось для человека, потом что от него нужно и в каком порядке. Жаргон («ветка», «PR», «вливание», «канбан»), номера коммитов и пути не идут в текст, пока их можно заменить делом («изменения сайта ждут вашей проверки»). Ссылка `repo#N «заголовок»` стоит в конце пункта, как адрес, а не как подлежащее. Одна мысль на пункт, без пересказа внутренней кухни агентов.

## Настройка: Manager Config

До первого использования задай это в `AGENTS.md` проекта (предпочтительно) или в `CLAUDE.md` (совместимость). Конфига агента у проекта ещё нет — запусти `corp-doctor`, он создаст или починит его. Владелец, репозитории, пути и номера досок берутся только отсюда.

```markdown
## Manager Config

### GitHub owner
Имя пользователя или организация GitHub для поиска issue:
- owner: your-github-handle

### Repos to scan (cross-repo issue search scope)
Репозитории, в которых manager ищет:
- ~/Projects/main
- ~/Projects/ops
- ~/Projects/marketing

### Tasks index file (optional)
Путь к курируемому индексу текущей недели. Manager читает его ПЕРВЫМ, до любого `gh search`, чтобы сузить запросы:
- tasks_index: ~/docs/tasks.md
(если файла нет — manager работает без индекса, поиск идёт по всем repos)

### Tasks directory (optional)
Путь к файлам дня и планам недели, которые создаёт weekly-planning:
- tasks_dir: ~/docs/tasks/

### Domain → repo routing
| Domain | Repo |
|--------|------|
| коммерция / B2B-сделки | crm |
| запуски продуктов | main |
| эксплуатация / инфраструктура | ops |
| контент | marketing |

### GitHub Projects integration
Место на доске — инвариант (см. «Железные инварианты»). Объяви свои доски:
- weekly_project: <number>          # общая доска «всё активное на этой неделе» по всем репозиториям
- weekly_project_owner: your-github-handle
- status_field: Status              # поле single-select, в котором хранится колонка
- status_in_progress: In progress   # имя (или id) опции активной колонки
- domain_projects (optional):       # доски по доменам, если они у тебя есть
    | Domain | Project number |
    | коммерция | <number> |
    | продукт | <number> |

ID доски, поля и опций живут только в `config.json` скрипта `gh_issue.sh` (пример: `config.example.json` в папке скилла, команды поиска id: [references/script.md](references/script.md) → «Конфиг»). В этот файл id не переписывай.

### W-label convention (optional)
- enabled: true
- format: W{NN} (ISO week)
(если false — manager создаёт issues без W-label)

### Standing write authorization
- mode: ask-each-time | execute-after-plan
(по умолчанию: ask-each-time — показать план и спросить. execute-after-plan — выполнить записи после показа краткого плана. В обоих режимах спрашивай при настоящей неоднозначности или жёстком блокере)

### CRM integration (optional)
- crm_path: ~/Projects/crm
- crm_pointer_format: [[<slug>]]
(если не используется — секция игнорируется; см. references/crm.md)
```

`corp-doctor` — скилл первичной настройки и починки этого конфига. Тип работы живёт в лейблах, эпике и на доске (см. [references/titles.md](references/titles.md)).

## Железные инварианты

Каждый issue, который трогает manager, соблюдает первые три; активный issue текущей недели ещё 4–6; PR с результатом седьмой:

1. **W-label** — текущая или будущая неделя либо неделя события с датой, если W-label включён в конфиге. Лейбла нет в репозитории — создай его.
2. **Эпик** — ровно один, через GitHub Sub-issues API. Каждый issue, который сам не эпик, привязан к эпику. См. [references/parent-epic.md](references/parent-epic.md).
3. **Трек задают заголовок и эпик.** Лейблы — только W-label и лейблы типа работы.
4. **Место на доске** — активный issue текущей недели стоит на доменной доске (если она есть) и на недельной доске. W-label без места на доске = `Project drift`.
5. **Эпик виден на доске** — для активного дочернего issue текущей недели эпик сам стоит на нужной доске с непустой колонкой статуса.
6. **Комментарий о работе**: в записи, когда над issue в этой сессии шла реальная работа: комментарий в таймлайн с итогом и ссылками на коммиты; он пишется в дополнение к смене колонки, лейбла или места на доске. Синк только лейбла или доски без работы над задачей обходится без комментария. Запись о работе с визуальным результатом (интерфейс, страница, схема) несёт картинку: `gh_issue.sh shot REF --image shot.png` даёт ссылку по SHA коммита, `comment REF --body-file F --image-url URL` вставляет её. Результат скрипта или правила показывай текстом: блок кода с выводом или таблица.
7. **Результат в PR**: PR с визуальным результатом (интерфейс, страница, схема) показывает картинку прямо в описании. Ссылка на картинку идёт по SHA коммита (`gh_issue.sh shot` печатает готовую) или вложением GitHub, по имени ветки не ставится: после удаления ветки такая ссылка битая. PR со скриптом или правилами показывает результат текстом: вывод команды блоком кода или таблицей. Описание обновляет `gh pr edit N --body-file F`. Без картинки или текстового вывода PR человеку на вливание не отдаётся. См. [references/script.md](references/script.md) → «Результат в PR».

Эпика нет ни в одном репозитории — manager до синка показывает это в плане и предлагает создать новый эпик или выбрать существующий. После синка у каждого issue есть эпик.
