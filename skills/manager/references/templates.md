# Тело issue: критерий готовности и шаблоны

Справочник уровня 2. Читать, когда создаёшь issue, переформатируешь тело, обновляешь его при синке или пишешь комментарий. Имена разделов и полей в шаблонах (`## Related`, `## Updates`, `**Status:**`, `**Next:**`, `**Verified:**` и др.) оставлены как в исходной версии скилла; язык повествования — по правилу «Язык заголовков issue» в [modes.md](modes.md).

## Оглавление

- Критерий готовности — тело должно быть проверяемым
- Шаблон тела (при создании)
- Шаблон обновления тела (по умолчанию)
- Шаблон комментария (только запасной канал)

## Критерий готовности — тело должно быть проверяемым

Когда manager **создаёт** issue или **переформатирует** существующий, тело ОБЯЗАНО содержать проверяемые критерии завершения.

**Обязательный минимум:**
1. **Конкретный чек-лист объёма `- [ ]`** — что именно входит в объём, каждый пункт наблюдаем как сделан / не сделан.
2. **Явное «считается сделанным, когда…»** — условие закрытия, привязанное к проверяемому артефакту или наблюдаемому поведению.
3. **Указатель на источник объёма** — откуда взялся объём: раздел скилла, отчёт исследования, slug в CRM, родительский эпик, транскрипт встречи.

**Расплывчатые однострочники без конкретики ЗАПРЕЩЕНЫ.** Тело issue, которое нельзя сверить с реальностью, = испорченное.

- ❌ `Внедрить правила из отчёта X` — непонятно, какие правила, какой файл и когда сделано.
- ✅ чек-лист `- [ ]` из конкретных пунктов + `сделано, когда правила записаны в <skill>/SKILL.md § …` + ссылка на исходный отчёт.

Если manager трогает существующий расплывчатый issue (однострочник без критерия готовности), он в том же синке добавляет чек-лист объёма + условие приёмки + указатель на источник. Это часть стандартного синка записи под постоянной авторизацией.

## Шаблон тела (при создании)

До записи любого тела в **публичный** репозиторий: замени приватные абсолютные пути, внутренние slug, личные handle, факты оплат, сырые URL встреч и переписок и доказательства, существующие только локально, на безопасные публичные указатели. Если безопасного публичного указателя нет, запиши приватный указатель только в приватный или внутренний репозиторий-владелец. Покажи это как блокер в плане синка, когда это применимо.

```markdown
<одна строка контекста: что изменилось / что сделано>

**Source artifact:** <кликабельный URL на GitHub — закоммичено и запушено>
**Date:** <YYYY-MM-DD>
**Track:** <ссылка на карточку CRM, если коммерческое — см. crm.md>

## What was done
<2-4 пункта — реальный прогресс>

## Scope
- [ ] <конкретный пункт, наблюдаемый как сделан / не сделан>
- [ ] <конкретный пункт>

## Next step
<одна строка — что закрывает этот issue (условие приёмки)>

## Related

- <repo>#N «человекочитаемый заголовок» — коротко, зачем ссылка

**Verified:** <YYYY-MM-DD> by manager

---
Synced by manager from session <YYYY-MM-DD>.
```

Добавляй блок `## Related` **только когда есть проверенные контекстные ссылки** — если их нет, опускай весь блок (не оставляй его пустым или с текстом-заглушкой).

## Шаблон обновления тела (по умолчанию)

```markdown
<одна строка контекста: что изменилось / что сделано — как раньше, освежи, если объём изменился>

**Status:** <active / blocked / pending external / done — «done» только если пользователь так сказал>
**Next:** <одна строка, следующий конкретный шаг — освежать при каждом синке>

[... остальное исходное содержимое тела — УДАЛИ любой старый блок `## Related` до перезаписи ...]

## Related

- <repo>#N «человекочитаемый заголовок» — коротко, зачем ссылка

**Verified:** <YYYY-MM-DD> by manager

## Updates

- **YYYY-MM-DD:** <2-4 пункта прогресса / решений> (code: <repo>@<sha>)
- **YYYY-MM-DD:** <предыдущая запись синка, сохранена>
```

Удали устаревший блок `## Related` из сохраняемого исходного содержимого, потом вставь не больше одного свежего проверенного блока (опусти, если настоящих контекстных ссылок нет). Новое обновление — сверху `## Updates`, старое — снизу (выбери порядок один раз на issue и держись его).

## Шаблон комментария (только запасной канал)

```markdown
**YYYY-MM-DD:** <одна строка заметки, которая не ложится в тело — например, «внешний блокер до X», «наблюдение временного состояния»>
```

Комментарий о работе (обязательный случай) перечисляет, что сделано в этой сессии + `refs`/SHA. Комментарии держи короткими. Если комментарий вырос больше 4 строк — ему место в теле.
