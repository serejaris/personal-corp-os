# Формат вывода

Справочник уровня 2. Читать перед тем, как показать пользователю план синка, отчёт о результате или ответ режима чтения.

## Оглавление

- Формат ссылки на issue (ВАЖНО)
- Режим записи — план (ДО выполнения)
- Режим записи — отчёт (ПОСЛЕ выполнения)
- Режим чтения

## Формат ссылки на issue (ВАЖНО)

**Показывая issue пользователю, всегда пиши в форме `<repo>#N — «человеческий заголовок»`.** Голый `<repo>#27` нечитаем — пользователю нужен заголовок, чтобы узнать трек с одного взгляда.

- ❌ Плохо: `<repo>#27 → комментарий + W19`
- ✅ Хорошо: `<repo>#27 «<трек-A> — ответ на бриф» → комментарий + W19`

## Режим записи — план (ДО выполнения)

Компактный план. Каждая строка: что сделаю + где + зачем. Группируй по трекам. Под каждым треком первая строка — **эпик** (родительский issue), потом sub-issues с маркером `parent: OK / parent: MISSING`. Решения и неясности — прямо в строке, вопросами.

```
План синка (W18, <дата>):

<трек-A> · эпик crm#15 «<трек-A> — обзор B2B-сделки»
- crm#27 «<трек-A> — ответ на бриф»  [parent: crm#15 ✓; W18 ✓; Project ✓]
  → обновить тело + комментарий о работе; статус → In progress
- crm#25 «<трек-A> — подготовка к встрече <дата>»  [parent: crm#15 ✓; W18 ✓; Project ⚠️ нет]
  → комментарий «обе встречи прошли»; добавить в Project; закрыть, если объём выполнен, иначе оставить открытым с причиной

Создать лейблы: W19 в $YOUR_OWNER/crm
Эпики без покрытия: (нет)

Не закоммичено в crm: meetings/<дата>.md (новый) — закоммитить до синка?

Выполняю по постоянной авторизации. Если объём выглядит неверно — стоп / поправь.
```

Если у трека **нет рабочего эпика**, покажи отдельно:

```
⚠️ Нет эпика: у трека «<X>» нет родительского эпика. Варианты:
   - Создать crm#NEW «<X> — обзор» как зонтик; все 3 issue ниже станут его sub-issues.
   ИЛИ
   - Взять существующий <repo>#N «<заголовок>» (sub_summary total=N) — спросить, если неоднозначно.
```

## Режим записи — отчёт (ПОСЛЕ выполнения)

```
Готово:
- crm#27 «<трек-A> — ответ на бриф» — обновлено тело + комментарий о работе + W19; parent crm#15 ✓; Project → In progress
- crm#42 «<трек-B> — объём расширен» — создан, дочерний crm#10, W18+W19, добавлен в Project
- лейбл W19 создан в $YOUR_OWNER/crm

Пропущено по твоему решению: crm#25 «<трек-A> — подготовка…» — оставлен открытым
```

## Режим чтения

Компактная таблица — всегда с колонкой «Заголовок», родительский эпик в отдельной колонке, колонка Project, без голых номеров:

```
Запрос: «что по <трек-A>»

Эпик трека: crm#15 «<трек-A> — обзор B2B-сделки» (3/5 сделано)

Открытые sub-issues:
| Issue | Заголовок | Родитель | W-label | Project | Активность | Статус |
|-------|-----------|----------|---------|---------|------------|--------|
| crm#27 | <трек-A> — ответ на бриф | crm#15 ✓ | W18 ✓ | ✓ | <дата> | Активен — КП до <дата> |
| crm#25 | <трек-A> — подготовка <дата> | crm#15 ✓ | W18 ✓ | ✓ | <дата> | Обе встречи прошли — вероятно, устарел |
| presentations#9 | <трек-A> — аудит деки | — ⚠️ | W18 ✓ | ⚠️ | <дата> | Нет родителя + нет в Project, привязать к crm#15 |

В индексе задач:
- 🔥 W18 приоритет 4 — «КП для <трек-A> до <дата>»

Не покрыто (пробел):
- Нет issue на написание самого КП (только подготовка). Создать при следующем синке?

Проверка здоровья трека:
- 1 issue без родительского эпика — presentations#9. Привязать при следующем синке.
- 1 issue нет в Project — presentations#9.

Дрейф в индексе / состоянии эпика:
- (по желанию) эпик crm#15 — 5/5 sub-issues сделаны, state OPEN. Кандидат на закрытие.

Отсеяно (ложные совпадения):
- crm#1 «<несвязанное> — готово» — найден по лейблу W18, к <трек-A> не относится
```

Когда у трека многоуровневая иерархия эпиков (корень → колонки/дочерние → внуки), выводи отчёт режима чтения **деревом, а не плоским списком**: в каждой строке статус родителя, статус W-label и место в Project. Активные issue текущей недели без места в Project помечаются `Project mismatch`.
