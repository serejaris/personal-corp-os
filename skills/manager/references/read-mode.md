# Режим чтения (запрос)

Справочник уровня 2. Читать, когда выбран режим чтения («что по треку X», «статус Y»): алгоритм, живое чтение состояния Project, доказательство родителя, связанный контекст, ложные совпадения. Режим чтения никогда не пишет в GitHub.

## Оглавление

- Алгоритм режима чтения
  - Живое чтение состояния Project — пакетный GraphQL
  - Неоднозначность доказательства родителя
  - Связанный контекст, не иерархия
- Ложные совпадения (режимы чтения И записи)

## Алгоритм режима чтения

1. Определи предмет запроса — имя трека, человек, репозиторий, номер issue, временное окно.
2. Запусти поиск по репозиториям (по нескольким ключам) — один `gh search issues` для простых треков, пакетный GraphQL для 3+ ключей (см. [search.md](search.md)).
3. **Отсей ложные совпадения** — выбрось совпадения, где пересечение по ключевым словам случайно (например, issue с лейблом `W18`, но не относящийся к запрошенному треку). См. «Ложные совпадения» ниже.
4. Для настоящих совпадений возьми живое состояние одним пакетным вызовом GraphQL: заголовок, состояние, лейблы, родитель (Sub-issues API), `projectItems` с колонкой статуса, последняя активность. Текст — не доказательство, используй живые чтения.
5. **Определи эпик трека** — найди родительский эпик. Возьми `sub_issues_summary` — отметь `total`, `completed`, `percent_completed` + собственный `state` эпика.
6. Сверь с индексом задач — есть ли трек в списке приоритетов текущей недели? Если да, пометь «🔥 hot W{NN}». Проверь строку индекса на дрейф: указанный issue CLOSED, расхождение объёма или подразумеваемая открытая работа, которой больше нет.
7. Вывод: сжатая таблица (с колонкой Project) + открытые вопросы + пробелы «что ещё не покрыто» + дрейфы. Режим чтения никогда не пишет в GitHub.

### Живое чтение состояния Project — пакетный GraphQL

Когда показываешь или правишь место в Project, бери до ~20 issue одним вызовом GraphQL через алиасы:

```bash
gh api graphql -f query='
query {
  i1: repository(owner:"$YOUR_OWNER", name:"<repo1>") { issue(number:<N1>) { ...IssueState } }
  i2: repository(owner:"$YOUR_OWNER", name:"<repo2>") { issue(number:<N2>) { ...IssueState } }
}
fragment IssueState on Issue {
  number title state url
  labels(first:20){nodes{name}}
  parent { number title repository { nameWithOwner } }
  projectItems(first:10){nodes{ id project { number title } fieldValueByName(name:"Status"){ ... on ProjectV2ItemFieldSingleSelectValue { name } } }}
}' | jq -r '(.data // {}) | to_entries[] | .value.issue | select(. != null)
  | "\(.number) \(.title) [\([(.labels.nodes // [])[].name]|join(","))] parent=\(.parent.repository.nameWithOwner // "—")#\(.parent.number // "") projects=\([(.projectItems.nodes // [])[] | "\(.project.title):\(.fieldValueByName.name // "empty")"]|join(" | "))"'
```

Заметки: передавай вывод в отдельный `jq`, **а не** через флаг `--jq` (см. ВАЖНОЕ в разделе о пакетном поиске в [search.md](search.md) — когда ответ GraphQL несёт `errors`, `gh` игнорирует `--jq` и вываливает сырое тело). `parent` — родитель из Sub-issues API; `projectItems[].fieldValueByName.name` — колонка статуса. Результат лежит в `.data.<alias>.issue` — не забудь уровень `.issue` в jq. Запасной вариант для одного issue: `gh issue view N -R $YOUR_OWNER/<repo> --json projectItems` — `.projectItems[].status` это объект; читай `.status.name`, а не `.status`. Список дочерних эпика: `gh api repos/$YOUR_OWNER/<repo>/issues/<EPIC_N>/sub_issues --jq '.[] | {number, title, repository_url}'`.

### Неоднозначность доказательства родителя

При проверке видимости родителя смотри и `parent_issue_url` дочернего, И эндпоинт `/sub_issues` родителя. Если со стороны дочернего родитель читается как `null`, а `/sub_issues` родителя перечисляет дочерний, сообщай `parent proof: parent sub_issues ✓; child API ambiguous` — не `parent missing`. Две поверхности API могут временно расходиться.

### Связанный контекст, не иерархия

Список контекста `Related` строй только для настоящих совпадений с отдельным объёмом: отдельная задача, контекстная ссылка, зависимость, артефакт в другом репозитории или историческая задача. Отсей связи родитель/дочерний, уже выраженные через Sub-issues API, — они и так видны в колонке иерархии. Не дублируй выраженную в API структуру текстом в `Related`.

## Ложные совпадения (режимы чтения И записи)

Поиск по W-label или общим словам может вернуть issue, у которых **общий лейбл, но они не на этом треке**. Пример: `<repo>#1` вернулся на запрос по `<трек-A>`, потому что у обоих лейбл `W18`.

**Правило:** если у найденного совпадения в заголовке или теле нет пересечения с запрошенным треком, кроме W-label или другого общего лейбла, — это ложное совпадение. Убери его из результатов и покажи в отчёте под `IGNORED (false positives)`, чтобы пользователь подтвердил.

```
IGNORED (false positives):
- <repo>#1 — найден по лейблу W18, но трек = <несвязанный трек>
```

Не отсеивай молча — покажи, что отсеяно и почему, на случай если пользователь заметит настоящую связь, которую manager пропустил.
