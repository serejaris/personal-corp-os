# Правила родительского эпика

Справочник уровня 2. Читать при создании issue, при синке и при проверке иерархии: что считается эпиком, как его найти, агрегирующие issue, видимый в Project корень, блок `Related`, проверка до синка.

## Оглавление

- Что считается эпиком
- Один эпик на issue
- Найти эпик — алгоритм при создании и синке
- Агрегирующий родитель для issue на несколько треков
- Видимый в Project корень
- Связанные issue — раздел тела
- Никаких лейблов-треков
- Проверка до синка

Каждый issue (кроме самого эпика) обязан иметь **ровно одного** родителя через GitHub Sub-issues API. Это машиночитаемое различение треков — оно заменяет лейблы-треки и устаревающие markdown-указатели в теле.

## Что считается эпиком

- Issue, у которого есть sub-issues (счётчик `N / M` вверху)
- В заголовке обычно объём трека (`<программа>: <партнёр> — обзор`, `<сделка> — обзор`, `<продукт> — поставка <версия>`)
- У самого эпика НЕТ родителя — он корень дерева
- У рабочего эпика обычно `total >= 1`, но новый корневой issue с ясным объёмом трека можно предложить и использовать как эпик до его первого sub-issue, если пользователь подтвердил объём (запуск нового трека).

## Один эпик на issue

GitHub поддерживает только одного родителя через Sub-issues API. Это совпадает с правилом «один трек — одна иерархия». Если задача вроде бы относится к двум трекам — пересмотри объём: вероятно, это два issue, ИЛИ это агрегирующий issue (см. ниже).

Не пиши в теле markdown `Parent: #N`, `Epic: #N`, `Belongs to: #N`, когда родитель задан через API, — это дубль, который устаревает. Родитель хранится только через Sub-issues API.

## Найти эпик — алгоритм при создании и синке

1. **Найди существующий эпик** трека поиском по репозиториям; проверь, что у кандидатов непустой `sub_issues_summary.total`.
2. **Каноническая привязка по домену** (настраивается под твой бизнес в `Domain → repo routing`):

   | Домен трека | Где живёт эпик |
   |-------------|----------------|
   | Образовательная программа / партнёрство | репозиторий учебного домена |
   | B2B-сделка / многоколонный коммерческий трек | crm / коммерческий репозиторий |
   | Запуск продукта | собственный репозиторий продукта |
   | Исследовательская инициатива | репозиторий исследований |

3. **Если эпика нет** — manager поднимает это в предложении: «у трека X нет эпика, создать?». Никогда не создаёт issue без родителя молча.
4. **При создании sub-issue** через API:

   ```bash
   CHILD_ID=$(gh api repos/OWNER/REPO/issues/CHILD_NUMBER --jq '.id')
   gh api -X POST repos/EPIC_OWNER/EPIC_REPO/issues/EPIC_NUMBER/sub_issues -F sub_issue_id=$CHILD_ID
   ```

## Агрегирующий родитель для issue на несколько треков

Если issue покрывает 2+ соседних трека, объёма или класса результатов, до назначения родителя классифицируй его как **агрегирующий issue**. Не прикрепляй его к первому подходящему предметному эпику, если из-за этого другой соседний объём станет невидимым.

**Признаки агрегирующего issue:**
- Заголовок или тело явно охватывает несколько соседних объёмов: `продукт + продажи`, `стратегия + поставка`, `пилот + документация`, `запуск + эксплуатация`.
- Issue живёт в агрегирующем или отчётном репозитории, а предметные эпики — в своих репозиториях-владельцах.
- Тело говорит о недельном обзоре, решении закрыть или остановить, прогнозе, воронке, операционном обзоре, срезе портфеля или координации между репозиториями.
- Issue обновляет общий индекс, прогноз, heartbeat, дашборд или план, а не один конкретный результат.

**Алгоритм:**
1. Найди предметный эпик для каждого соседнего объёма.
2. Найди агрегирующий эпик в этом репозитории: `forecast`, `pipeline`, `portfolio`, `weekly review`, `operating review`, `coordination`, `umbrella`.
3. Если нашёлся — прикрепи issue к нему. В плане и отчёте пиши `parent: aggregate`.
4. Если такого нет — покажи предложение: создать зонтичный issue ИЛИ разделить на отдельные дочерние issue под каждым предметным эпиком.
5. Никогда не делай один issue дочерним двух эпиков; родитель в GitHub ровно один.

В выводе чтения и записи явно различай типы родителя:
- `parent: track` — конкретный эпик предметного домена
- `parent: aggregate` — зонтик прогноза / воронки / портфеля / операционного обзора
- `parent: runtime` — эпик опубликованного / рабочего слоя
- `parent: unknown` — родитель ещё не найден или нужен выбор пользователя

## Видимый в Project корень

Manager различает три понятия родителя:

- **Родитель в API** — прямой родитель из GitHub Sub-issues API (`parent_issue_url`).
- **Видимый корень** — ближайший родитель / обзор трека / зонтичный issue, который должен быть в текущем Project view и под которым пользователь раскрывает дерево.
- **Исторический / бэклог-прародитель** — верхний стратегический родитель, который может оставаться вне недельного Project view, когда у видимого корня уже есть W-label и непустая колонка статуса.

**Правила:**
1. Если у активного issue текущей недели нет sub-issues и он дочерний issue поставки или действия, его родитель в API или видимый корень обязан быть в Project с непустой колонкой статуса.
2. Если issue сам является обзором трека / сессионным родителем / зонтиком (`sub_issues_summary.total > 0`) и уже виден в Project, его бэклог- или стратегический прародитель не обязан появляться в недельном Project. Сообщай как `parent: historical/backlog`.
3. Если у дочернего есть `parent_issue_url`, но элемента родителя нет в Project view, показывай как `Project divergence: parent epic not visible`.
4. Если API со стороны дочернего показывает `parent: null`, проверь по списку `/sub_issues` вероятного эпика. Если дочерний там есть, считай это доказательством — но отметь `parent proof: parent sub_issues` (GitHub может читать иерархию несимметрично).
5. Если Project view фильтрует по репозиторию или типу так, что родитель физически не может появиться, сообщай `Project view limitation` и не переподчиняй дочерний.

## Связанные issue — раздел тела

`Related` / `Related issues` в теле — только для контекстных перекрёстных ссылок. Иерархию он никогда не создаёт.

- Иерархия живёт только в GitHub Sub-issues API (`parent_issue_url`, `sub_issues_summary`).
- Связанные ссылки — для контекстных отсылок, отдельных зависимостей, артефактов в других репозиториях и исторических задач.
- Блок Related можно удалить без потери владельца, W-label, места в Project или дерева sub-issues.

**Запрещено внутри блока Related:** `Parent: #N`, `Epic: #N`, `Belongs to: #N`, ручные списки дочерних и подзадач, зеркало статуса, зеркало следующего шага, W-label, подсказки о месте в Project, состояние чек-листа.

**Формат тела:**
```markdown
## Related

- <repo>#N «человекочитаемый заголовок» — коротко, зачем ссылка

**Verified:** YYYY-MM-DD by manager
```
Максимум 3 ссылки-пункта + одна строка `Verified`. При каждом синке тела переписывай блок по живому поиску — не дописывай бесконечно.

**До записи тела с разделом Related — проверь вживую каждый упомянутый issue:**
```bash
gh issue view N -R OWNER/REPO --json title,state,url,labels,updatedAt
gh api repos/OWNER/REPO/issues/N --jq '{parent: .parent_issue_url, sub_summary: .sub_issues_summary}'
```
Для активных ссылок текущей недели проверь ещё и `projectItems`.

Если какой-то ссылки нет, она закрыта, без родителя, указывает на другой трек, с устаревшим W-label или утянет приватные данные или данные CRM в публичный репозиторий — покажи `Related links divergence` и убери или сообщи до записи тела. Для публичных репозиториев: не копируй приватные заголовки, slug из CRM, локальные пути, личные handle, факты оплат и приватные URL — используй безопасную публичную метку вроде `private CRM issue — context only`, а точный приватный указатель держи в приватном репозитории или отчёте.

## Никаких лейблов-треков

Лейблы-треки (`<track-slug>`, `<client>-deal`) НЕ создаются. Различение треков идёт через заголовок + принадлежность к эпику. Существующие старые лейблы-треки не удаляются (это история), но новые не создаются. Навигация по треку между репозиториями = sub_issues эпика + доска Project, а не фильтр по лейблу.

## Проверка до синка

До `gh issue edit` / `gh issue create` агент ОБЯЗАН проверить родителя существующего issue и, для активных issue, его место в Project:

```bash
gh api repos/OWNER/REPO/issues/N --jq '{parent: .parent_issue_url, sub_summary: .sub_issues_summary}'
```

Покажи в предложении, у каких issue нет родителя и какой эпик предложен для каждого.
