# Частые ошибки и антипаттерны

Справочник уровня 2. Читать перед выполнением плана синка и при сомнении, можно ли сделать запись. Две части пересекаются по смыслу намеренно: таблица «ошибка → исправление» и короткий список запретов.

## Оглавление

- Частые ошибки
- Антипаттерны

## Частые ошибки

| Ошибка | Исправление |
|--------|-------------|
| Закрывать issue без явной команды пользователя | По умолчанию — комментарий и оставить открытым. Закрывать, только если пользователь сказал «закрой» или объём полностью выполнен И пользователь упомянул завершение. |
| Закрывать issue поставки после одной локальной проверки | Проведённый лайв / сессия / воркшоп не считается поставленным, пока: записан ID записи или артефакта либо точный блокер, проверен рабочий / опубликованный артефакт (не только локально) и проходит проверка URL, который видит пользователь. Иначе оставь открытым с точным открытым дочерним. Не выводи запись на курс или оплату из числа просмотров — сверяй с главным источником. |
| Удалять старые лейблы (`retro:W17` и т.п.) «для порядка» | Не снимай лейблы, которые не ставил. Добавь новый W-label, старые оставь. |
| Ставить один W-label задаче на несколько недель | Если задача охватывает текущую + следующую неделю, ставь оба. |
| Создавать новый issue, когда подходит комментарий в существующем | Сначала ищи широко (несколько ключей / пакетный GraphQL). Создавай, только если объём явно расходится. |
| Пропускать создание W-label, когда его нет в репозитории | Железный инвариант — создай лейбл (быстрый путь), не пропускай. |
| Создавать или трогать issue без родительского эпика | Железный инвариант — покажи в предложении, не молчи. |
| Считать W-label достаточным | Нужны W-label + родитель + место в Project (колонка не пустая). |
| Считать родителя в API достаточным | Проверь элемент видимого корня в Project и его колонку статуса. |
| Прикреплять один issue к двум эпикам | GitHub поддерживает одного родителя. Раздели на два issue или считай агрегирующим. |
| Markdown `Parent: #N` в теле, когда есть ссылка в API | Дубль, устаревает. Родитель — только через Sub-issues API. |
| Нет SHA, когда коммиты есть | Запись в `## Updates` обязана перечислять короткие SHA коммитов сессии по каждому затронутому репозиторию. |
| Локальный путь `~/...` как ссылка на результат | Сначала коммит + push; ссылка в теле и отчёте — кликабельный URL на GitHub. |
| N×`gh issue view` по одному | Используй пакетный GraphQL; одиночные вызовы — только точечный запасной вариант. |
| Закрывать или синкать после реальной работы без комментария о работе | Железный инвариант 6 — добавь комментарий в таймлайн. |
| Не соблюдать ворота публичного репозитория | До записи в публичный репозиторий не добавляй приватные / CRM / личные данные; если не уверен — покажи в предложении и спроси. |
| Считать индекс задач общим списком задач для правки | Индекс курирует пользователь / `weekly-planning`; manager правит только строки затронутых issue, чистку при закрытии и явный ремонт дрейфа. |
| Считать незакоммиченные локальные изменения «сделанными» | Покажи незакоммиченную работу в отчёте; не ссылайся на ещё не запушенный артефакт. |
| Молча отсеивать ложные совпадения | Убери из основных результатов, но покажи в `IGNORED (false positives)`. |
| Считать каждый вызов режимом записи | Сначала проверь: артефакты (запись) ИЛИ вопрос о состоянии (чтение)? Используй схему выбора режима. |
| Просить пользователя самому открыть URL, issue или файл | Никогда. Принеси содержимое сам через `gh issue view <repo>/<N> --comments`. |
| Голые номера issue | Всегда `<repo>#N «заголовок»`. Номера неузнаваемы. |

## Антипаттерны

- **Создавать issue без родительского эпика** — ломает железный инвариант. Покажи в предложении, не создавай сироту.
- **Создавать новые лейблы-треки** — больше не делается. Различение = заголовок + принадлежность к эпику.
- **Доменный префикс в заголовке** — устарел. Метаданные типа живут в лейблах / дереве родителей / Projects.
- **Прикреплять один issue к двум эпикам** — один родитель на issue. Пересмотри объём или считай агрегирующим.
- **Markdown `Parent: #N` / `Epic: #N` в теле, когда родитель задан через API** — дубль, устаревает.
- **Считать текст доказательством места в Project** — используй живые чтения `projectItems`, а не «должен быть на доске».
- **Автоматически закрывать устаревшие issue** — никогда. Покажи пользователю, оставь открытым.
- **Широко переписывать индекс задач** — manager правит только строки затронутых issue, чистку при закрытии и явный ремонт дрейфа. Структура недели принадлежит `weekly-planning`.
- **Молча пропускать дрейф индекса задач** — показывай явно, чтобы пользователь перекурировал.
- **Молча пропускать эпик, открытый после завершения** — эпик со 100% сделанных sub-issues, но `state = open` — настоящий сигнал; показывай как кандидата на закрытие, никогда не закрывай автоматически.
- **Один мега-комментарий со всей сессией** — один комментарий на issue, в рамках трека этого issue.
- **Создавать issue в нескольких репозиториях на один артефакт** — один артефакт = один основной issue.
- **Пропускать поиск** — всегда ищи до создания. Перекос в сторону обновления.
- **Вываливать в чат полный вывод расследования** — чтения молчаливые; видно только предложение.
- **Просить пользователя заново перечислить артефакты сессии** — выводи из контекста разговора.
- **Голые номера issue** — всегда `<repo>#N «заголовок»`.
- **Пропускать индекс задач перед gh search** — pre-flight не опционален.
- **Добавлять комментарии вместо обновления тела** — тело — основной канал; комментарий — только для записи о работе или действительно временных заметок.
