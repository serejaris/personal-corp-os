# SEO-аудит с перекрёстной проверкой

В SEO-ревью модель ошибается двумя способами: выдумывает проблему, которой на сайте нет, и раздувает мелочь до «критично». Скилл ставит между отчётом и починкой проверку: каждую находку подтверждает или снимает критик, который смотрит на живой сайт и не знает автора отчёта.

Метод вырос из разбора двадцати отчётов разных моделей на одном сайте: [Какая из 20 моделей лучше всех делает SEO-аудит](https://sereja.tech/blog/kakaya-model-luchshe-seo-audit/).

## Роли

| Роль | Агент | Что делает |
|---|---|---|
| Оркестратор | сессия, где вызван скилл | ведёт шаги, хранит таблицу «буква → автор», сводит вердикты |
| Аудитор | [`seo-reviewer`](../../agents/seo-reviewer.md) | пишет отчёт «топ-10 ошибок», сайт и репозиторий не меняет |
| Критик | [`blind-critic`](../../agents/blind-critic.md) | проверяет находки обезличенных отчётов, выносит вердикт каждой |
| Ревьюер | [`uncle-bob`](../../agents/uncle-bob.md) | проверяет PR с починкой |
| Редакторы | [`ilyakhov`](../../agents/ilyakhov.md), [`tufte`](../../agents/tufte.md) | правят тексты страниц и подачу данных в отчёте |

## Что нужно до начала

- Адрес сайта и его исходники в git.
- Сеть у агентов: проверка идёт запросами `curl` к живому сайту.
- Выгрузка Search Console за три месяца, если у владельца есть доступ. Владелец экспортирует её сам. В репозиторий выгрузку не кладут.

## Ход

### 1. Зафиксировать снимок

Записать адрес сайта, коммит исходников и дату. Все аудиторы и критики работают по одному снимку. Без него находку «устарела» нельзя отличить от находки «неверна».

### 2. Собрать отчёты

Запустить параллельно от двух до пяти аудиторов `seo-reviewer`. Задание одно на всех, слово в слово:

```text
Проведи SEO-ревью сайта <адрес> и найди топ-10 ошибок.
Исходники: этот репозиторий, коммит <sha>.
Проект не меняй: без файлов, коммитов, пушей и PR.
```

Независимость дают разные модели или отдельные сессии: аудиторы отчётов друг друга не видят. Одинаковое задание важнее хитрого промпта, потому что только так отчёты можно сравнить.

Каждый отчёт сохранить файлом во временной папке вне репозитория сайта.

### 3. Обезличить

Переименовать отчёты в `A.md`, `B.md` и дальше. Убрать из текста имя модели и подписи. Таблицу «буква → автор» оставить у оркестратора: критикам она не нужна.

### 4. Слепая проверка

Запустить двух критиков `blind-critic` независимо друг от друга. Каждый получает все отчёты, адрес сайта, коммит и выгрузку Search Console, если она есть. Критик сводит находки в один список без повторов и проверяет каждую командой.

| Что ставит критик | Значения |
|---|---|
| Вердикт | подтверждена · неверна · частично · не проверить |
| Вред | высокий · средний · низкий · нет |
| Отметка | вред в отчёте преувеличен |

### 5. Свести вердикты

| Критики | Что делать |
|---|---|
| оба «подтверждена» | в список на починку |
| оба «неверна» | снять и записать причину в ложные находки |
| расходятся | перепроверить одной командой и приложить её вывод |
| «не проверить» | закрыть выгрузкой Search Console или отдать вопросом владельцу |

### 6. Показать владельцу

Один список: находка, класс, вред, команда с выводом, предложенная правка. Ложные находки идут отдельной короткой таблицей с причиной. Что чинить, решает владелец.

### 7. Починить

Три PR, файлы которых не пересекаются, их можно вести параллельно:

| PR | Что входит |
|---|---|
| Индекс и редиректы | `robots.txt`, sitemap, правила редиректов в конфиге хостинга |
| Шаблоны и разметка | `<head>`, canonical, Open Graph, JSON-LD, даты |
| Перелинковка и содержание | ссылки, каталоги и списки, тонкие страницы |

Каждый PR дописывает журнал `docs/seo-changelog.md`: дата, что изменили, по какой находке, чем проверить.

```markdown
## 2026-11-09

- Добавили canonical на страницы раздела `/guides/`. Находка 3.
  Проверка: `curl -s https://example.com/guides/first/ | grep -io '<link rel="canonical"[^>]*>'`
```

Через месяц журнал сопоставляют с графиком Search Console: видно, какая правка что дала. Каждый PR проходит ревью `uncle-bob`, новые и переписанные тексты страниц проходят `ilyakhov`.

### 8. Проверить после выкладки

Повторить команды из шага 4 по каждой починенной находке. Вывод записать в журнал рядом с правкой.

## Четыре класса находок

| Класс | Что смотреть |
|---|---|
| Индекс | `robots.txt`, sitemap, canonical, `noindex`, служебные страницы в индексе, тонкие страницы |
| Ссылки | битые внутренние ссылки и картинки, страницы без входящих ссылок, разделы вне каталога и поиска |
| Разметка и даты | `title`, `description`, Open Graph, JSON-LD, хлебные крошки, `lastmod` и даты публикации |
| Редиректы | цепочки из двух шагов и длиннее, постоянный или временный код, `www` и слэш в конце, старые адреса |

Команды проверки:

```bash
curl -sI https://example.com/page/
curl -sIL https://example.com/old/ | grep -Ei '^(HTTP|location)'
curl -s https://example.com/robots.txt
curl -s https://example.com/sitemap.xml | grep -c '<loc>'
curl -s https://example.com/page/ | grep -Eio '<link rel="canonical"[^>]*>|<meta name="robots"[^>]*>'
curl -s https://example.com/page/ | sed -n '/<head>/,/<\/head>/p' | grep -Eio '<title>[^<]*</title>'
```

## Типовые ложные находки

| В отчёте | На деле | Как отличить |
|---|---|---|
| «На странице два `<title>`» | второй `<title>` лежит внутри `<svg>` | считать `<title>` только в `<head>` |
| «Мёртвая ссылка» | адрес отвечает 200 | `curl -sIL` на адрес |
| «Правило редиректа ловит все адреса» | у правила есть условие по хосту | прочитать правило в конфиге целиком |
| «Страницы выпали из sitemap» | владелец скрыл их намеренно | найти флаг в исходниках или спросить владельца |
| «Проблема из прошлого года» | её уже починили | проверить сегодня командой |
| «Сотни битых ссылок», «критическая утечка» | число и оценка без доказательства | требовать команду и её вывод |

## Сравнить аудиторов

Когда аудит заодно выбирает модель, оркестратор раскрывает буквы после шага 5 и строит рейтинг.

- Главное мерило: ценность верных находок, в первую очередь тех, которых нет у других.
- Ошибка в топ-3 штрафуется сильнее ошибки в хвосте списка.
- Длина отчёта очков не даёт.
- Место ставится по среднему из рейтингов двух критиков. Рядом пишут время и цену прогона.

## Правила

- Аудиторы и критики сайт и репозиторий не меняют. Запрет стоит в задании явно: без него модель на задаче ревью может запушить ветку.
- Находка без команды и вывода в список на починку не попадает.
- Выгрузку Search Console и таблицу «буква → автор» в публичный репозиторий не кладут.
- Один PR закрывает один класс находок.
